The Seven-Adapter Ceiling

An LLMInferenceService stops accepting LoRA adapters at seven, and fails silently when it does. Here is what actually causes it, what each way out costs, why the right answer depends on which gateway you ship - and why the cheapest option was never on the list of shapes.

The object the ceiling lives in

One LLMInferenceService generates one HTTPRoute with twelve rules. Eleven of them are fixed. The twelfth grows with every adapter you add.

What breaks

And why it does not look broken.

Gateway API caps a single rule at 64 matches, and the template puts eight matches per adapter into rules[4]: four endpoints, each with a trailing-slash twin.

The apiserver's answer, verbatim:

The dangerous part is what happens next. The rejection lands inside a dry-run defaulting call before the real apply, so the previously applied route keeps serving. Existing adapters carry on working, the new one is simply invisible, and the only signal is a condition on the CR. A service can sit in that state indefinitely, which is why this reaches production having passed every test with three adapters.

Reducing the adapter list prunes correctly: measured live, 8 adapters down to 3 takes the rule from 64 matches to 32, and down to 1 takes it to 16. But clearing spec.model.lora entirely does not. The route keeps the last adapter's matches, naming something that no longer exists, and reports HTTPRoutesReady=True while doing it. Filed as #279.

The ceiling used to be twelve

kserve #5826 consolidated four per-endpoint routing rules into one, to free three rule slots. The reasoning was sound and the arithmetic went the wrong way: rule slots were never scarce (12 of 16 used), and matches were. Folding four rules into one moved the binding constraint from the route-wide 128 back onto the per-rule 64, and the ceiling fell from twelve to seven.

What actually addresses an adapter

Before optimising the rule that causes the ceiling, it is worth asking what it is for. The answer reprices every option in this document.

kserve registers each adapter with vLLM under two body-level names: the bare name and the fully qualified one. vLLM never sees an HTTP header.

When body and header disagree, the body wins every time, and a header with no body model is a 400. X-Gateway-Model-Name does not select the adapter and never did. It exists so an HTTPRoute can match on the requested model, because Gateway API cannot route on a request body.

Which means the ceiling is optional

rules[4] and rules[11] are the only two that scale with adapter count, and they exist purely to serve that header. Switching model-based routing off makes stripModelBasedRoutingRules remove both:

Verified live: with the rules gone, all three path+body forms still resolved to the adapter. The seven-adapter ceiling disappears entirely and nothing that works today stops working.

So is there a gap in the routing layer?

Yes, and it is the opposite of what the ceiling suggests. Adapters are not hard to address; they are addressable today at zero match cost. The gap is on the producer side of header addressing:

  • kserve consumes X-Gateway-Model-Name - matches on it, expands it, strips it - but nothing in kserve produces it
  • a body-based router is the intended producer, reading model from the body and setting the header, and none is deployed here or shipped by kserve
  • no OpenAI SDK sets a non-standard routing header, so in practice only a hand-crafted client can use this mode
  • on OpenShift AI the mode is refused outright by deny-misrouted-model-header
what this does and does not mean

The entire match budget, and every shape in this document, is spent on the consumer half of a body-based-routing design whose producer half does not exist yet. The rules are not wrong - a shared /v1/chat/completions endpoint serving many models is exactly what the Gateway API Inference Extension is for - they are early.

This retracts no measurement above. It reprices them: every ceiling here is the cost of a feature that is not finished, and the cheapest option was never on the list of shapes. If and when a body-based router ships, the ceiling returns and the shape question becomes live again.

nested 7 → unbounded recommended

Serve adapters beneath the base model; match one 44-character prefix.

  • Adapter count leaves the route arithmetic entirely: 19 matches, constant
  • The only shape that programmed identically on both data planes at any size
  • Renames nothing, keeps path scope, needs no body-based router or ConfigMap
  • Prefix anchoring proven safe on both: model-b does not capture model-b-instruct
  • Changes the model string clients send. The real cost, and it is not in any budget table
  • Couples adapter names to the base model name
alternation 7 → 320 data-plane dependent

List the names that already exist in one regex. Change nothing else.

  • Zero behaviour change: byte-identical across all 72 probes and all 13 endpoint-picker outcomes
  • No renamed rule, no renamed model, nothing a client sees
  • Anchored exactly on both data planes: adapter-a1 matches, adapter-a1x does not
  • Reaches 6 adapters on kgateway, which is fewer than today. The RE2 program-size limit is a data-plane setting; Istio and Envoy Gateway raise it, kgateway does not
  • Pattern is rewritten whenever the adapter set changes, so route churn stays
split 7 → 12

Revert #5826. Four rules again, one per endpoint.

  • Provably zero behaviour change across all 72 probes
  • Returns to a state that shipped for months
  • Renames a rule 1→4, and that rename cannot be safely aliased
  • Spends 3 of the 4 remaining rule slots for a 5-adapter gain
split-noslash 7 → 22 portable

Split, and drop the trailing-slash duplicates.

  • Triples the ceiling for exactly one moved probe, with no regex at all so no data plane can refuse it
  • The twins only compensate for an undocumented Exact match choice
  • Same 1→4 rename problem as split
  • Header-addressed /v1/completions/ stops reaching the pool
prefix 7 → 15

Use PathPrefix, as the path rules already do.

  • Renames nothing, so no policy migration at all
  • Closes an addressing inconsistency that has no stated reason
  • Broadens into stateful sub-resources that carry no model
  • Lowest ceiling of the realistic options
collapse 7 → 58

Drop the path from the routing rule entirely.

  • Large ceiling with no naming change
  • Real cost smaller than it looks: 2 changed outcomes, not 20
  • Gives up path scope, reversing a deliberate decision in #5087
  • Sends /health and /metrics through a scheduler

why the trailing-slash twins exist

Only because the header rules use Exact. PathPrefix /v1/completions already matches /v1/completions/ and everything below it; Exact matches one literal string, so it needs a twin. The path rules have used PathPrefix since the start and never needed one. Nothing documents the choice, and it is what doubles the paths axis.

Where a row shows falls through, no rule in this route matched, and the request went on to whatever else is attached to the gateway. Renames rules, client-visible strings change and works on kgateway are the rows that decide this. split pays in policy migration. alternation pays nothing at all until you move it off Istio, at which point it pays everything. nested pays once, in client naming, and is the only shape that both survives an arbitrary data plane and stops the route being rewritten every time an adapter changes.

why "unaliasable" is the sharp word

Renaming a rule detaches any Kuadrant policy pinned to it by sectionName. That is recoverable when the rename is one-to-one: put the old name back and enforcement returns. But split turns one rule into four, so a single alias can only cover one of them. Tested: the policy came back reporting Accepted=True, Enforced=True while actually covering a quarter of its former traffic. A green policy with a 75% hole is worse than the clean break, which at least reports TargetNotFound.

This only affects policies someone wrote themselves against our rule names. odh-model-controller's own policies target whole objects and are unaffected.

What adopting nested would ask for

The only shape that removes the ceiling permanently, and the only one whose cost is not a routing decision. Worth being precise about what you would be signing up to.

why this is back on the table

Both design docs proposed nesting specifically as the alternative to an alternation regex, on the grounds that an alternation blows Envoy's RE2 program-size limit. Measured on Istio that looked wrong, because Istio raises the limit to 32768 and an alternation reaches 320 adapters there. Measured on kgateway, which leaves Envoy's default of 100, the same shape reaches six. The docs were arguing about portability and they were right. Nesting's pattern is 44 characters whatever the adapter count, so no program-size limit can reach it.

Today an adapter is registered with vLLM under a name that sits beside the base model. nested puts it underneath:

ID the served name
# today - base and adapter are siblings, so the route must list both
publishers/<ns>/models/llama-3-8b

# nested - one prefix covers the base and everything under it
publishers/<ns>/models/llama-3-8b
publishers/<ns>/models/llama-3-8b/adapters/sql-adapter

That string is what a caller puts in the request body:

PY what a client changes
client.chat.completions.create(
    model="publishers/my-ns/models/sql-adapter",                  # before
    model="publishers/my-ns/models/llama-3-8b/adapters/sql-adapter",  # after
)

The business ask, concretely

A one-time public naming change

Every caller that names an adapter changes one string. Notebooks, saved app configs, eval harnesses, benchmark scripts, anything with a model name written down. No CRD conversion reaches a string a client hard-coded, so this is communication, not migration tooling.

A changed /v1/models response

Anything doing discovery - a dashboard, a catalogue, a downstream router - sees new identifiers. If something stores a model name, it needs to be re-fetched rather than assumed stable.

Accepting a new coupling

Adapter identity now contains base-model identity, so renaming spec.model.name renames every adapter with it. Today those are independent. After nesting, a base-model rename becomes a breaking change for all adapter clients, which is worth a policy rather than a surprise.

A status field listing routable adapters

Under nesting the adapter name never appears in the HTTPRoute, so the route stops being the place you can learn which adapters are actually routable. Nothing else answers that today. This is small, but it is real work and it is not optional.

A deprecation window, and someone to own it

The migration is additive if sequenced: kserve already registers two names per adapter, so register three and both old and new work at once. Nothing breaks until the route stops matching the legacy names, but the budget win only arrives when they are dropped. Someone has to decide when that is, and tell people.

What you get for it

  • Adapter count leaves the route arithmetic entirely: 19 matches, constant, at any number of adapters
  • No body-based router, no mapping ConfigMap, no sync window, no extra component to operate
  • Path scope preserved, so /health and /metrics stay off the scheduler
  • No rule renamed, so no policy migration
  • Per-adapter route churn disappears entirely: adding an adapter does not touch the HTTPRoute at all, measured as a zero-line diff

The questions that decide it

  1. Do we control the gateway, or does someone else?

    On a product that ships Istio, alternation reaches 320 without touching a public name, and this conversation can wait. On anything that has to run against an arbitrary Gateway API implementation it reaches six, and no amount of route arithmetic fixes that. This is the question that decides, and it is not a routing question.

  2. Is per-adapter route churn a problem in its own right?

    alternation still rewrites the pattern every time the adapter set changes, so every add or remove reprograms Envoy. nested is the only shape where it does not. That is a separate argument from both the ceiling and the portability, and it holds even if the other two go away.

  3. Are we willing to change a public model identifier once?

    That is the entire remaining cost. Not a routing risk - anchoring and blast radius were measured and are clean - a product one. Header-addressed adapter routing has close to no adoption today, and on OpenShift AI that traffic is refused outright, so the cheapest moment is now and it gets dearer as adoption grows.

the honest summary

nested is cheap technically and expensive socially. Everything that could have made it risky - prefix anchoring against a neighbouring model name, regex program size, blast radius on the data plane - was tested and came back clean. What is left is a naming decision, and that is not a routing call to make.

the consequence for this decision

Header addressing does not work on OpenShift AI today. Every request in the header column of the earlier matrix is refused before routing. So rules[4], the rule that causes the entire seven-adapter ceiling, currently serves only traffic ODH rejects. The budget it consumes is real; the traffic is not.

That reprices the options. collapse and prefix only change header-addressed behaviour, so on ODH they change nothing observable: their "20 moved" and "8 moved" are moves within traffic that is already denied. nested is the exception, because it changes the model identifier itself, which the live addressing modes carry in the request body.

where alternation sits

It does not interact with this policy at all. The deny rule tests the header value against ^publishers/[^/]+/models/.+$ and the request path against the publisher prefix. alternation changes neither: the values it matches are the same strings, on the same paths, and the policy targets the whole route rather than a sectionName, so no rule rename can detach it. It is the one shape that is a no-op from the authorization side, which is the same reason it is a no-op from the client side.

Worth noting the same cross-tenant hole this spike measured was found independently on that side and closed there. The deny rule exists because a per-participant path carrying another tenant's model header would be authorized by the path (tenant A) but routed by the header (tenant B). Upstream kserve without odh-model-controller still has it open.

Their stated plan is body-based routing with resolvedPath normalization, rewriting /v1/… plus a header into publisher form so it can be authorized rather than denied. That is the route by which header addressing becomes supported, and it makes the header family a cross-repo dependency rather than a kserve-local choice.

Two services, one adapter name

Not a budget question, but it constrains how many adapters you can usefully run in one namespace, so it belongs here.

fullyQualifiedModelName is publishers/{ns}/models/{name} with no service name in it (router_discovery_filter.go:35). Two services in a namespace that each define an adapter called sql-adapter therefore both generate a route matching publishers/{ns}/models/sql-adapter.

HR measured: svc-a and svc-b both define shared-adapter

Every request carrying that header went to svc-a, 6 of 6. svc-a's route was created two seconds earlier, which is exactly Gateway API's documented tie-break: oldest route wins. svc-b's own adapter is unreachable by name, and nothing in the data path indicates which one you got.

kserve does detect this

findModelNameCollisions (router_validation.go:278) covers adapter names, and the controller raises a ModelNameCollision warning Event. Detection was added in kserve#5800 and works. An earlier pass in this investigation reported that nothing objected, which was wrong: it checked CR conditions, and the warning is an Event.

but the message names the wrong thing

The event always formats Spec.Model.Name, while findModelNameCollisions returns peer service names rather than the overlapping model names. So an adapter collision reports the base model: here it said "model-a" when the actual overlap was shared-adapter, and model-a overlaps with nothing. It fires correctly and points at the wrong object, which is how a real signal gets dismissed as spurious. Filed as #284.

This matters for the budget discussion because it caps the useful adapter count per namespace, not per service. Raising one service's ceiling to 297 does not help if two services in that namespace want the same adapter name, and neither alternation nor nested changes that. nested does narrow it, since an adapter name is then qualified by its base model, and two services with different base models stop colliding.

The second data plane, which changes the answer

Every regex finding above was measured on Istio. Installing kgateway and Envoy Gateway beside it, and replaying the same patterns against all three, produced one result that transfers cleanly and one that does not transfer at all.

Gateway API does not specify whether a RegularExpression header match is a full match or a partial one, and everything here depends on the answer. What is not portable: how far the pattern can grow

the finding that reverses the recommendation

Envoy refuses to compile a regex whose RE2 program size exceeds a configured limit, and each implementation picks that value. That is the same failure shape as the CEL rejection at the top of this document, one layer further down and with even less to look at.

So the answer depends on what you ship

The design docs were right, and my earlier correction to them was wrong. They rejected an alternation because it would blow the default RE2 program-size limit, and proposed a short fixed prefix regex instead. That is exactly what happens on kgateway. What I measured was Istio's raised limit, and I generalised it into a claim about the option rather than about one data plane.

and then a third implementation corrected that too

Envoy Gateway also raises the limit - it disables the check outright - and programs 300 adapters where kgateway refuses at seven. So two of three implementations are fine and kgateway is the odd one out, which is the opposite of what two data planes suggested. The risk is unchanged: the limit is a per-deployment setting Gateway API does not specify and kserve does not control, and one shipping implementation leaves it somewhere the alternation cannot live. But "alternation is Istio-only" was too strong. The accurate version is that it depends on a data-plane setting one major implementation gets wrong.

nested's pattern is 44 characters and constant, so its program size does not depend on adapter count at all. It programmed on both implementations and routed correctly on both. That is the property the docs were reaching for, and it is worth more than the ceiling number.

the limit is a knob, but not one kserve owns

re2.max_program_size.error_level is an Envoy runtime setting, so a platform that controls its own gateway can raise it. OpenShift AI ships Istio, where it is already 32768. Upstream kserve cannot assume that about an arbitrary Gateway API implementation, which is what makes this a distribution-level decision rather than a routing one.

What the regex costs at request time

Separate question from whether it compiles, and the answer is reassuring: essentially nothing.

The first attempt failed, and the failure is worth showing because it is the obvious experiment. Comparing max-throughput QPS across shapes on a kind cluster produced numbers that were not monotonic in pattern size - alternation@150 looked 32% slower than the floor while alternation@297 looked only 8% slower. That is not a measurement, it is a laptop.

So amplify the signal instead. Every configuration below forces a known number of header evaluations that all miss, then lands on the same terminal rule, so the only difference between two rows is the work done in between. Configurations rotate position each rep so warm-up drift cannot alias onto config order, and the estimator is the minimum p50 across eight reps rather than the median, because interference can only ever add time.

The largest positive reading, 0.145 µs per evaluation, is therefore an upper bound rather than a cost. The shipped shape performs one evaluation per request. The mechanism is why it is safe to extrapolate. RE2 compiles to a DFA, so match cost is O(length of the input), and the input is a 45-byte header value no matter how many alternatives the pattern lists. Pattern size costs compile time once, at config load, and memory. It does not cost per-request time. The program-size limit above exists to bound that memory, not to bound latency.

Writing the pattern so it fits and does not churn

Every byte is an adapter not served, and every needless difference is an Envoy reprogram. Three things worth changing:

RX escaping, measured on Istio
formemitsbytesadapters
re.escapeadapter\-a14091297
minimaladapter-a14092320

Python's re.escape escapes -, which RE2 does not need outside a character class. Kubernetes names are DNS-1123, so the alphabet is [a-z0-9.-] and . is the only member that means anything to a regex. Escaping only that, with a strict allowlist and a fall back to full escaping for anything outside it, is 23 more adapters for no loss of safety. Verified on Istio: 320 applies and routes, 321 is rejected by the apiserver.

Sort the names. The pattern is built in spec order, so reordering the adapter list in YAML produces a different string, a different route object and an Envoy reprogram for a change that altered nothing. Sorting makes the pattern a function of the set rather than the sequence, and removes a class of reconcile churn that is otherwise very hard to attribute.

You cannot make it readable in place. RE2 has no free-spacing mode. Tested rather than assumed - a (?x) pattern takes the whole RouteConfiguration down, and Istio says so:

! istio proxy, verbatim
rejected: invalid perl operator: (?x
and do not factor the alternation into a trie

adapter-a1|adapter-a2|… compresses beautifully to adapter-a(1|2|…), and both the byte count and the RE2 program size would drop sharply. It is a mirage. The synthetic names share a prefix precisely because they are generated, and that is the same trap that made kgateway look like it reached 220. Optimising against the benchmark's naming inflates the published number without helping any real deployment.

So a 4KB pattern is one unbroken line in kubectl get httproute -o yaml whatever we do, and the only mitigation is to make reading it unnecessary. Which raises a question the ceiling tables cannot answer.

what follows for nested

A status field listing routable adapters stops being a nice-to-have and becomes required, because nothing else can answer the question - the route object no longer knows. That is not an argument against nesting. It is a line item that belongs in its cost alongside the naming change, and it was missing from the decision brief above.

Why the limit lands where it does

Six adapters sounds arbitrary until you know what RE2 is counting. It is arithmetic, and once you can do it the rest of this document stops being surprising.

What "program size" means

RE2 does not backtrack. It compiles a pattern into a program: a flat list of instructions that a DFA simulation walks. RE2::ProgramSize() returns roughly that instruction count, and for a pattern that is mostly literal text it works out at about one instruction per byte.

Envoy caps it. The google_re2 matcher checks the compiled program against the runtime key re2.max_program_size.error_level, and Envoy's built-in default is 100. Not 100 characters by intent, but for literal text that is what it amounts to: your regex may be about 100 characters.

Where the 100 goes

The alternation's budget, spent before any adapter is named:

RX the pattern, by cost

└──────── 30 bytes ─────────┘ └─ 7 ─┘ └──── ~10 each ────┘

The namespace prefix costs 30 of the 100 before a single adapter is named. The base model takes 7 more. That leaves roughly 60 instructions, and a realistic adapter name is about 10. Hence six. The ceiling is not really about adapters at all: it is about how many characters are left after publishers/{namespace}/models/ has taken its share, which means a longer namespace name lowers it further.

this is not a kgateway bug, and kgateway is the outlier

kgateway ships Envoy with stock defaults and does not set the key at all. Two other implementations do, so it is kgateway that is unusual:

Why the synthetic names hid it

At 280 generated names, 3,572 bytes of pattern, the program size was only 111. RE2 factors shared prefixes when it compiles, so adapter-a1|adapter-a2|…|adapter-a280 collapses to roughly adapter-a plus a digit trie - nearly free. Real adapter names do not rhyme, so nothing factors and every name costs its full length.

One rule explains both numbers: program size tracks the distinct literal content left after factoring, not the length of the pattern you wrote. It is also why "compress the alternation into a trie" is a trap rather than an optimisation - it would be tuning against the benchmark's naming, and real deployments would get none of it.

And why nested is immune

RX constant, whatever the adapter count
publishers/lora\-budget/models/model\-a(/.*)?
44 bytes  →  ~45 instructions  →  under 100 forever

The adapter count is not in the pattern, so it cannot push the program size anywhere. nested has always been under the default limit and always will be. That is exactly the property the design docs were reaching for when they asked for "a single fixed prefix regex, constant size, well under the default RE2 program-size limit". They were not making a rough argument about pattern length; they were making a precise one about program size, and it was correct.

what this means for anyone implementing it

A pre-flight check that counts matches and bytes is not enough. Bytes are what the CRD caps; program size is what the data plane caps, and the two diverge by a factor of thirty depending on how much the names happen to share. The check has to compile the pattern, or the failure lands where nothing is watching: HTTPRoute Accepted=True, Envoy NACKing the config, last good route still serving.

Does the path axis need the same trick?

The header rules need a regex to stay constant. A fair question is whether the path rules do too. Today they do not, and the reason is worth being explicit about.

Every path rule keys on the service name or the base model name, and neither multiplies by adapter count. Ten of the twelve rules sit at one match each no matter how many adapters exist. That is exactly why the seven-adapter ceiling is a header problem and not a path problem.

confirmed against the captured route

An adapter has no publisher path at all. /publishers/{ns}/models/adapter-a1/v1/chat/completions matches nothing in the service's route and falls through to whatever else is on the gateway. Adapters have only ever been addressable by naming them in the request body.

Why it is still worth asking

Because of the authorization finding above. On OpenShift AI the header family is denied outright, and publisher paths are the only authorized way to address a model. So an adapter has no authorized path-based address today: it is reachable only via /{ns}/{name}/v1/… with the adapter named in the body, which authorizes as the instance rather than the model. Giving adapters a publisher path is a plausible consequence of that authorization model, and it would put them on the path axis for the first time.

Three things fall out of that table.

The byte cap is four times tighter on paths

Gateway API sets HTTPPathMatch.Value to MaxLength 1024 and HTTPHeaderMatch.Value to 4096. So the alternation buys 32 to 75 here, against 7 to 320 on the header axis. Same trick, a quarter of the room.

PathPrefix cannot express it

A prefix match has no wildcard, so /publishers/{ns}/models/*/v1/completions is not sayable. Collapsing adapter paths requires RegularExpression, which means the path axis inherits the whole RE2 program-size exposure - on kgateway a 1,018-byte path pattern is refused exactly as the header one is.

Nesting is constant on both axes

/publishers/{ns}/models/{base}(/adapters/[^/]+)?{endpoint} is 76 bytes whatever the adapter count, because the adapter name sits in a wildcard segment instead of being enumerated. The same property that makes the nested header pattern constant shows up independently here.

the strongest argument for nesting in this document

Every other shape is linear on both axes and needs a separate trick on each. Nesting is the only one that is constant on both, and it gets there for the same structural reason each time: the adapter name stops being something the route has to enumerate. That is a property of the naming scheme, not of the routing, which is why it does not show up in any budget table and why it survives a data plane that caps regex complexity.

Recommendation

One question comes before the shapes, and then the data planes split the rest into two answers: one for a product that controls its own gateway, one for upstream kserve which does not.

first, check whether you are paying for anything

The two rules that cause the ceiling exist only to serve X-Gateway-Model-Name, which nothing in kserve produces, no OpenAI SDK sets, and ODH denies. Adapters are fully reachable today by path plus body at zero match cost. If header addressing has no producer in your deployment, setting serving.kserve.io/model-based-routing-enabled: "false" removes the ceiling outright - 12 rules and 37 matches down to 10 and 10, measured, with every working request unchanged. Everything below is what to do when that is not an option, or once a body-based router ships and the mode becomes real.

  1. Fix the pruning bug and add a pre-flight check

    Unchanged by everything below, and needed under every shape. Clearing spec.model.lora leaves the route carrying an adapter that no longer exists, while reporting ready. And nothing counts the budget before applying, which is why exceeding it arrives as a raw CEL string rather than a condition. If a regex shape is adopted, the check has to count RE2 program size too, not just matches and bytes, because that is the limit the data plane enforces and it enforces it silently.

  2. Upstream: nested is the answer, and the docs said so

    It is the only shape that is portable, unbounded, keeps path scope, renames no rules and stops the route being rewritten per adapter. Its pattern is 44 characters and constant, so no program-size limit can reach it. Measured identical on Istio and kgateway, anchoring exact on both. The cost is a one-time change to a public model identifier, and that is a product decision rather than a routing one. The window for making it is now, while header-addressed adapter routing has close to no adoption.

  3. Before that lands: split-noslash portably, alternation on Istio

    split-noslash reaches 22 with no regex at all, so no data plane can refuse it, at the cost of one moved probe and a rule rename that detaches sectionName policies. Where you control the data plane - Istio and Envoy Gateway both raise the RE2 limit, and OpenShift AI ships Istio - alternation reaches 320 with zero behaviour change, no rename and no naming migration. Take it there, gated on the program-size check, and never as an upstream default.

what changed, and what I got wrong

This document has been wrong twice about the same thing, in opposite directions. First it recommended alternation outright, having measured only Istio's raised RE2 limit and generalised it. Then kgateway refused at six adapters and it swung to "Istio is the outlier". Envoy Gateway then turned out to raise the limit too, so kgateway is the outlier and two of three implementations are fine. Each correction came from adding one more implementation, which is the argument for not stopping at two - and the reason the endpoint-picker findings below, still measured on Istio alone, should be read with suspicion.

the counter-intuitive bit that survived

split still looks free - zero behaviour change - and is still the only family that triggers the migration hazard, because it renames a rule one-to-four and that rename cannot be safely aliased. If you are going to pay a rename, pay it for split-noslash's 22 rather than split's 12; the extra moved probe is a trailing-slash path no OpenAI client emits.

Corrections to the design docs

Three numbers do not survive measurement. A fourth claim does, against my earlier reading of it.

  • #5826 lowered the ceiling from 12 to 7. It consolidated four rules into one to free three rule slots, trading match budget - the binding constraint - for rule budget, which was not scarce. 12 of 16 rule slots were in use.
  • The collapse reaches 63 adapters, not the roughly 122 estimated. The figure conflated the per-rule cap of 64 with the route-wide 128. Getting past 63 needs a match-splitter on top of the collapse.
  • The RE2 limit is not one number. The docs assume Envoy's default of 100. Istio sets 32768, Envoy Gateway disables the check, kgateway leaves the default. The objection is right about the risk and wrong about the prevalence, and neither doc says which data plane it is talking about.
  • The rejection of the alternation stands, on the risk if not the odds. This is a retraction of my own correction. On the strength of the Istio measurement I recorded the alternation as an option the docs had wrongly dismissed; on kgateway with realistic names it reaches six adapters, fewer than we have today. Two of three implementations are in fact fine with it, so "Istio-only" was too strong - but an upstream default still cannot depend on a setting one shipping implementation gets wrong, which is what the docs were arguing.

What this does not prove

Stated plainly, because the numbers above are otherwise easy to over-read.

  • The endpoint-picker findings are still Istio-only. The EPP bypass below 1.29 and the rule-name cross-wire were not retested on kgateway. Given that testing a second data plane is exactly what reversed the regex recommendation, these should be assumed Istio-specific until someone repeats them.
  • Two data planes is not "portable". Istio and kgateway are both Envoy. Nothing here says anything about a non-Envoy implementation, and the full-match header semantics that both rely on are unspecified by Gateway API rather than guaranteed by it.
  • The ODH authorization analysis is read, not run. Its policy denies header-addressed traffic outright, which would make the header family dead weight there, but that is source-reading rather than observation.
  • The latency figures come from one laptop. They bound the per-evaluation cost below what the rig can resolve, which is enough to rule the regex out as a request-time concern, but they are not a throughput model for a real cluster.
  • The adapter target is still unset. Every ceiling here is measured against a requirement nobody has fixed. If the answer is "under 20", split-noslash is the whole fix and the rest of this document is background.
