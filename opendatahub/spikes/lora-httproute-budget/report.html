The Seven-Adapter Ceiling

An LLMInferenceService stops accepting LoRA adapters at seven, and fails silently when it does. Here is what actually causes it, what each fix costs, and which one to take.

8 route shapes measured 72 routing probes 4 issues filed 3 corrections to the design docs

What breaks

And why it doesn't look broken.

The generated HTTPRoute encodes each adapter as a set of match rules. Gateway API caps a single rule at 64 matches, and the template puts eight matches per adapter into one rule:

adaptersmatches in the binding ruleroute totalresult
0819applied
33246applied
65673applied
76482at the cap
872—rejected

The apiserver's answer, verbatim:

rejection

spec.rules[4].matches: Too many: 72: must have at most 64 items

The dangerous part is what happens next. The rejection lands inside a dry-run defaulting call before the real apply, so the previously applied route keeps serving. Existing adapters carry on working, the new one is simply invisible, and the only signal is a condition on the CR. A service can sit in that state indefinitely — which is why this reaches production having passed every test with three adapters.

The ceiling used to be twelve

kserve #5826 consolidated four per-endpoint routing rules into one, to free three rule slots. The reasoning was sound and the change was behaviour-neutral — but it traded the wrong resource. Matches multiply per adapter, so concentrating them into one rule multiplies the growth rate against a cap that is per rule. Rule slots weren't scarce (12 of 16 used). Matches were.

rulesrouting layoutmax adapters
before #5826154 rules × 2 matches12
after #5826 (today)121 rule × 8 matches7

At zero adapters both versions are byte-identical. The damage is entirely in the derivative, which nothing measures — and the PR's own test used two adapters, where 24 sits comfortably under 64.

read the “probes moved” column carefully

It counts requests whose destination changed, which is not the same as requests that broke. Put a real endpoint picker in the path and the collapse's 20 moved destinations change only 2 outcomes — and both were already returning 404. “Moved” is a signal to look, not a cost.

split 7 → 12

Revert #5826. Four rules again, one per endpoint.

  • Provably zero behaviour change across all 72 probes
  • Returns to a state that shipped for months
  • Renames a rule 1→4, and that rename cannot be safely aliased
  • Spends 3 of the 4 remaining rule slots

split-noslash 7 → 22

Split, and drop the trailing-slash duplicates.

  • Triples the ceiling for exactly one moved probe
  • The twins only exist to compensate for an undocumented Exact match choice
  • Same 1→4 rename problem as split
  • Header-addressed /v1/completions/ stops reaching the pool

prefix 7 → 15

Use PathPrefix, as the path rules already do.

  • Renames nothing — no policy migration at all
  • Closes an addressing inconsistency that has no stated reason
  • Broadens into stateful sub-resources that carry no model
  • Lowest ceiling of the realistic options

nested 7 → unbounded

Serve adapters beneath the base model; match one prefix.

  • Adapter count leaves the route arithmetic entirely — 19 matches, constant
  • Renames nothing, keeps path scope, needs no BBR or ConfigMap
  • Prefix anchoring proven safe: model-a does not capture model-a-instruct
  • Changes the model string clients send — the real cost, and it isn't in any budget table
  • Couples adapter names to the base model name

collapse 7 → 58

Drop the path from the routing rule entirely.

  • Large ceiling with no naming change
  • Real cost is smaller than it looks — 2 changed outcomes, not 20
  • Gives up path scope, reversing a deliberate decision in #5087
  • Sends /health and /metrics through a scheduler

What the shapes actually look like

Every routing rule in every shape has the same form: a grid of paths × models. The models axis is 1 + adapters. That one fact explains the ceiling and every option for raising it.

Read that grid and the options stop being a list — each one attacks a different axis of the same multiplication.

why the trailing-slash twins exist

Only because the header rules use Exact. PathPrefix /v1/completions already matches /v1/completions/ and everything below it; Exact matches one literal string, so it needs a twin. The path rules have used PathPrefix since the start and never needed one. Nothing documents the choice — and it is what doubles the paths axis.

Where a request actually lands

The grid explains the budget. This explains the one behavioural difference that matters — what happens to a request carrying a model header on a path that isn't an inference endpoint.

Recommendation

Two things worth doing regardless, then one choice that depends on a number nobody has fixed yet.

  1. Fix the pruning bug and add a pre-flight check

    Removing adapters never shrinks the route, so the budget is sticky — a service that once had seven carries that cost after dropping to three. And nothing counts matches before applying. Both are needed under every shape below, and neither changes any behaviour.

  2. Take prefix or split-noslash for the near term

    prefix reaches 15 and renames nothing. split-noslash reaches 22 for one moved probe but renames a rule 1→4, which cannot be safely aliased. If nobody has pinned a policy to v1-model-routing, take split-noslash. If you can't be sure, take prefix.

  3. Decide whether you need more than ~22

    If yes, nested is the answer and the question becomes a naming decision, not a routing one. If no, stop — the route stops being the constraint and adapter count returns to being a GPU-memory question.

the counter-intuitive bit

split looks free — zero behaviour change — and is the only family that triggers the migration hazard. nested looks expensive — a user-visible naming change — and touches no rule name at all. The cheap-looking option carries the migration cost; the expensive-looking one doesn't.

What else this turned up

Four filed issues, three of which have nothing to do with the budget.

Filed

  • Identical rule names cross-wire the endpoint picker. Istio keys its inference-pool wiring by bare rule name; kserve names every service's rules identically. With three services on one gateway, 17 of 26 routes were scheduled by another service's picker, and every request with a body returned 500. Non-deterministic and sticky. (p1)
  • Istio below 1.29 never invokes the endpoint picker. It is deployed, healthy, resolved — and silently bypassed, with traffic round-robining instead of being scheduled. Bisected: 1.28 broken, 1.29 and 1.30 correct. (p2)
  • Removing adapters never prunes the route. Clear the LoRA spec entirely and 18 matches naming non-existent adapters remain, with the route reporting ready. (p2)
  • MaxAdapters documents a default that is never applied. Confirmed live: two adapters configured, vLLM running with max_lora=1. (p3)

Corrections to the design docs

  • The collapse reaches 63, not ~122 — the estimate conflated the per-rule cap with the route-wide one.
  • The regex objection that closed that track assumes Envoy's default program-size limit of 100. Istio sets it to 32768. A 932-character pattern works with no blast radius.
  • A renamed rule does not detach policies silently — Kuadrant reports TargetNotFound and names the section. But re-adding the old name on a 1→4 split restores a green policy covering a quarter of its former traffic, which is worse than the loud failure.

What this doesn't prove

Stated plainly, because the numbers above are otherwise easy to over-read.

  • Everything is Istio-only. The endpoint-picker findings, the 32768 regex limit and the rule-name collision were not retested on another data plane. None of them transfer to an upstream recommendation without that.
  • The ODH authorization analysis is read, not run. Its policy denies header-addressed traffic outright, which would make the header family dead weight there — but that is source-reading, not observation.
  • The adapter target is still unset. Every ceiling here is measured against a requirement nobody has fixed. If the answer is “under 20”, most of this document is moot and step 2 is the whole fix.
