The Seven-Adapter Ceiling

An LLMInferenceService stops accepting LoRA adapters at seven, and fails silently when it does. Here is what actually causes it, what each fix costs, and which one to take.

8 route shapes measured 72 routing probes 4 issues filed 3 corrections to the design docs

What breaks

And why it doesn't look broken.

The generated HTTPRoute encodes each adapter as a set of match rules. Gateway API caps a single rule at 64 matches, and the template puts eight matches per adapter into one rule:

adaptersmatches in the binding ruleroute totalresult
0819applied
33246applied
65673applied
76482at the cap
872—rejected

The apiserver's answer, verbatim:

rejection

spec.rules[4].matches: Too many: 72: must have at most 64 items

The dangerous part is what happens next. The rejection lands inside a dry-run defaulting call before the real apply, so the previously applied route keeps serving. Existing adapters carry on working, the new one is simply invisible, and the only signal is a condition on the CR. A service can sit in that state indefinitely — which is why this reaches production having passed every test with three adapters.

The ceiling used to be twelve

kserve #5826 consolidated four per-endpoint routing rules into one, to free three rule slots. The reasoning was sound and the change was behaviour-neutral — but it traded the wrong resource. Matches multiply per adapter, so concentrating them into one rule multiplies the growth rate against a cap that is per rule. Rule slots weren't scarce (12 of 16 used). Matches were.

rulesrouting layoutmax adapters
before #5826154 rules × 2 matches12
after #5826 (today)121 rule × 8 matches7

At zero adapters both versions are byte-identical. The damage is entirely in the derivative, which nothing measures — and the PR's own test used two adapters, where 24 sits comfortably under 64.

read the “probes moved” column carefully

It counts requests whose destination changed, which is not the same as requests that broke. Put a real endpoint picker in the path and the collapse's 20 moved destinations change only 2 outcomes — and both were already returning 404. “Moved” is a signal to look, not a cost.

split 7 → 12

Revert #5826. Four rules again, one per endpoint.

  • Provably zero behaviour change across all 72 probes
  • Returns to a state that shipped for months
  • Renames a rule 1→4, and that rename cannot be safely aliased
  • Spends 3 of the 4 remaining rule slots

split-noslash 7 → 22

Split, and drop the trailing-slash duplicates.

  • Triples the ceiling for exactly one moved probe
  • The twins only exist to compensate for an undocumented Exact match choice
  • Same 1→4 rename problem as split
  • Header-addressed /v1/completions/ stops reaching the pool

prefix 7 → 15

Use PathPrefix, as the path rules already do.

  • Renames nothing — no policy migration at all
  • Closes an addressing inconsistency that has no stated reason
  • Broadens into stateful sub-resources that carry no model
  • Lowest ceiling of the realistic options

alternation 7 → 320

List the existing names in one regex. Change nothing else.

  • Zero behaviour change — byte-identical across all 72 probes
  • No renamed rule, no renamed model, nothing a client sees
  • Anchored exactly: adapter-a1 matches, adapter-a11 does not
  • Tops out at 120–450 depending on name length, not truly unbounded
  • Pattern is rewritten whenever the adapter set changes, so route churn stays

nested 7 → unbounded

Serve adapters beneath the base model; match one prefix.

  • Adapter count leaves the route arithmetic entirely — 19 matches, constant
  • Renames nothing, keeps path scope, needs no BBR or ConfigMap
  • Prefix anchoring proven safe: model-a does not capture model-a-instruct
  • Changes the model string clients send — the real cost, and it isn't in any budget table
  • Couples adapter names to the base model name

collapse 7 → 58

Drop the path from the routing rule entirely.

  • Large ceiling with no naming change
  • Real cost is smaller than it looks — 2 changed outcomes, not 20
  • Gives up path scope, reversing a deliberate decision in #5087
  • Sends /health and /metrics through a scheduler

What the shapes actually look like

Every routing rule in every shape has the same form: a grid of paths × models. The models axis is 1 + adapters. That one fact explains the ceiling and every option for raising it.

Read that grid and the options stop being a list — each one attacks a different axis of the same multiplication.

why the trailing-slash twins exist

Only because the header rules use Exact. PathPrefix /v1/completions already matches /v1/completions/ and everything below it; Exact matches one literal string, so it needs a twin. The path rules have used PathPrefix since the start and never needed one. Nothing documents the choice — and it is what doubles the paths axis.

read these three rows together

Renames rules, client-visible strings change and route rewritten per adapter are the only rows that cost anything beyond the route object. split pays in policy migration. nested pays in client naming, and is the only shape that stops the route being rewritten every time an adapter changes. alternation pays in neither — it is the same constant-match trick as nested, applied to the names that already exist.

why “unaliasable” is the sharp word

Renaming a rule detaches any Kuadrant policy pinned to it by sectionName. That is recoverable when the rename is one-to-one — put the old name back and enforcement returns. But split turns one rule into four, so a single alias can only cover one of them. Tested: the policy came back reporting Accepted=True, Enforced=True while actually covering a quarter of its former traffic. A green policy with a 75% hole is worse than the clean break, which at least reports TargetNotFound.

This only affects policies someone wrote themselves against our rule names. odh-model-controller's own policies target whole objects and are unaffected.

What adopting nested would actually ask for

It is the only shape that removes the ceiling permanently, and the only one whose cost is not a routing decision. Worth being precise about what you would be signing up to.

Today an adapter is registered with vLLM under a name that sits beside the base model. nested puts it underneath: 

# today — base and adapter are siblings, so the route must list both
publishers/<ns>/models/llama-3-8b
publishers/<ns>/models/sql-adapter

# nested — one prefix covers the base and everything under it
publishers/<ns>/models/llama-3-8b
publishers/<ns>/models/llama-3-8b/adapters/sql-adapter

That string is what a caller puts in the request body:

client.chat.completions.create(
    model="publishers/my-ns/models/sql-adapter",              # before
    model="publishers/my-ns/models/llama-3-8b/adapters/sql-adapter",  # after
)
check alternation first

Both design docs proposed nesting specifically as the alternative to an alternation regex — “a single fixed prefix regex … unlike an alternation, which is not” — on the grounds that an alternation blows Envoy’s RE2 program-size limit. That limit is 32768 on Istio, not the 100 assumed, and the real bound turns out to be the 4096-byte cap on a header match value: 320 adapters, measured, with zero behaviour change and no naming migration at all. Everything below is still true, but it is only worth paying if 320 is not enough, or if removing per-adapter route churn matters on its own.

The business ask, concretely

A one-time public naming change

Every caller that names an adapter changes one string. Notebooks, saved app configs, eval harnesses, benchmark scripts — anything with a model name written down. No CRD conversion reaches a string a client hard-coded, so this is communication, not migration tooling.

A changed /v1/models response

Anything doing discovery — a dashboard, a catalogue, a downstream router — sees new identifiers. If something stores a model name, it needs to be re-fetched rather than assumed stable.

Accepting a new coupling

Adapter identity now contains base-model identity, so renaming spec.model.name renames every adapter with it. Today those are independent. After nesting, a base-model rename becomes a breaking change for all adapter clients — worth a policy, not a surprise.

A deprecation window, and someone to own it

The migration is additive if sequenced: kserve already registers two names per adapter, so register three and both old and new work at once. Nothing breaks until the route stops matching the legacy names — but the budget win only arrives when they are dropped. Someone has to decide when that is, and tell people.

What you get for it

  • Adapter count leaves the route arithmetic entirely — 19 matches, constant, at any number of adapters
  • No body-based router, no mapping ConfigMap, no sync window, no extra component to operate
  • Path scope preserved, so /health and /metrics stay off the scheduler
  • No rule renamed, so no policy migration
  • Per-adapter route churn disappears — adding an adapter stops rewriting the HTTPRoute

The questions that decide it

  1. Do we need more than roughly twenty adapters on one service?

    If no, split-noslash reaches 22 without touching a public name and this conversation ends. Nothing else here matters until that number exists.

  2. Are we willing to change a public model identifier once?

    That is the entire cost. Not a routing risk — anchoring and blast radius were measured and are clean — a product one.

  3. Can we reach the callers we have?

    Header-addressed adapter routing has close to no adoption today, and on OpenShift AI that traffic is refused outright by the authorization policy. The cheapest moment to change a public name is before anyone depends on it, and that window is open now — it closes as adoption grows.

the honest summary

nested is cheap technically and expensive socially. Everything that could have made it risky — prefix anchoring against a neighbouring model name, regex program size, blast radius on the data plane — was tested and came back clean. What is left is a naming decision, and that is not a routing call to make.

What OpenShift AI's authorization policy already decides

Read from odh-model-controller, not run — but it changes which of the shapes above can matter, so it belongs before the recommendation.

The design docs describe this policy as one SubjectAccessReview that parses the URL. It is now five rules, and one of them settles the header question outright: deny-misrouted-model-header is an immediate local 403 — no API round-trip — whenever a valid-looking model routing header appears on a path that is not a publisher path and not a batch path.

the consequence for this decision

Header addressing does not work on OpenShift AI today. Every request in the header column of the earlier matrix is refused before routing. So v1-model-routing — the rule that causes the entire seven-adapter ceiling — currently serves only traffic ODH rejects. The budget it consumes is real; the traffic is not.

That reprices two options. collapse and prefix only change header-addressed behaviour, so on ODH they change nothing observable — their “20 probes moved” and “8 probes moved” are moves within traffic that is already denied. nested is the exception: it changes the model identifier itself, which the live addressing modes carry in the request body.

Worth noting the same cross-tenant hole this spike measured was found independently on that side and closed there — the deny rule exists because a per-participant path carrying another tenant's model header would be “authorized by the path (tenant-A) but routed by the header (tenant-B)”. Upstream kserve without odh-model-controller still has it open.

Their stated plan is body-based routing with resolvedPath normalization, rewriting /v1/… plus a header into publisher form so it can be authorized rather than denied. That is the route by which header addressing becomes supported — and it makes the header family a cross-repo dependency rather than a kserve-local choice.

the part that surprised me

No URL changes. Adapters have never been addressable by path — an adapter lives on the same pool as its base model, so /{ns}/{name}/v1/chat/completions with {"model": "…sql-adapter"} already reaches it. Nesting changes the identifier in the body, not the address. That is why it survives ODH's authorization policy untouched, and why the change is narrower than “rename the routing scheme” suggests — but also why it still bites on ODH, where the body is exactly what the live addressing modes carry.

Recommendation

One no-regret fix, one shape that costs nothing, and a question that decides whether anything else is needed.

  1. Fix the pruning bug and add a pre-flight check

    Removing adapters never shrinks the route, so the budget is sticky — a service that once had seven carries that cost after dropping to three. And nothing counts matches before applying, which is why the failure arrives as a raw CEL rejection rather than a condition. Both are needed under every shape below, and neither changes any behaviour.

  2. Take alternation

    7 → 320 adapters for zero behaviour change. One regex listing the model names that already exist, in place of one Exact match each. Byte-identical across all 72 probes, no renamed rule so no policy migration, no renamed model so nothing a client sends changes, and anchoring verified exact. It is the same constant-match trick nested uses, applied to today's names instead of new ones.

  3. Only then ask whether 320 is short

    If it is — or if per-adapter route churn is a problem in its own right, since alternation still rewrites the pattern on every adapter change — nested is the answer and the question becomes a naming decision rather than a routing one. Otherwise stop: the route is no longer the constraint, and adapter count goes back to being a GPU-memory question.

why this changed

Both design docs proposed nested naming specifically as the alternative to an alternation, which they rejected because an alternation would blow Envoy's RE2 program-size limit. Measured, that limit is 32768 on Istio rather than the assumed 100, and the binding constraint is instead the 4096-byte cap on a header match value — which lands at 320 adapters, not two. The option was ruled out on a premise that does not hold here.

the counter-intuitive bit

split looks free — zero behaviour change — and is the only family that triggers the migration hazard, because it renames a rule one-to-four and that rename cannot be safely aliased. alternation is also zero behaviour change, renames nothing, and reaches 320 instead of 12. Where split looked like the cheap first step, it is now dominated outright.

Corrections to the design docs

Three numbers in the existing analysis do not survive measurement.

  • The collapse reaches 63 adapters, not the ~122 estimated — the figure conflated the per-rule cap of 64 with the route-wide 128. Getting past 63 needs a match-splitter on top of the collapse.
  • #5826 lowered the ceiling from 12 to 7. It consolidated four rules into one to free three rule slots, trading match budget — the binding constraint — for rule budget, which was not scarce.
  • The regex objection that closed that track assumes Envoy's default program-size limit of 100. Istio sets it to 32768. A 932-character pattern is accepted, routes correctly, and leaves neighbouring routes untouched.

What this doesn't prove

Stated plainly, because the numbers above are otherwise easy to over-read.

  • Everything is Istio-only. The endpoint-picker findings, the 32768 regex limit and the rule-name collision were not retested on another data plane. None of them transfer to an upstream recommendation without that.
  • The ODH authorization analysis is read, not run. Its policy denies header-addressed traffic outright, which would make the header family dead weight there — but that is source-reading, not observation.
  • The adapter target is still unset. Every ceiling here is measured against a requirement nobody has fixed. If the answer is “under 20”, most of this document is moot and step 2 is the whole fix.
